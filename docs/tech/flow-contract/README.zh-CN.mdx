## 1. 两方，三个位置

三个插件里只有它**有状态**。它的产物不留在插件里 —— 会装进消费方项目，而它们所处理的需求又住在那个项目之外。

| 位置 | 归属 | 是否进 git |
|---|---|---|
| `<project>/.flow/nodes/` · `.flow/genai/`（判定器**以及**两个 e2e 步骤拿来拷的记录模板）· `.flow/workflows/` · `.flow/config.yaml` | 插件 —— 由 `genai-init` 拷进来 | 不进：`genai-init` 会 ignore 整个 `.flow/`，因为它本身就是来源插件里已被版本管理的产物 |
| `<project>/Makefile`（`genai-metrics`）· `<project>/tools/genai/thresholds.json` · `e2e.json` | **项目** | 进 |
| `<project>_genai/backlogs/` · `archive/` —— 仓库的**同级兄弟目录** | 项目所有者 | 由他决定；不额外给的话它没有历史 |

**兄弟目录的名字是承重的。** 门命令拿不到任何变量，所以它只能按 `../$(basename "$PWD")_genai` 去定位需求目录。
换个名字会弄坏两道门，而且是**静默**弄坏。

## 2. 项目这一侧的契约

五项义务，其中只有三项是项目要写的文件：

| 义务 | 形状 | 缺了会怎样 |
|---|---|---|
| 一个 `genai-metrics` make 目标 | 打印一行，以 `genai-metrics: ` 开头，后面跟一个 JSON 对象；**退出码和其余输出一律忽略** | `genai.implement` 与 `genai.merge` 的门都返回 `metrics_missing`，并要求交给人处理 |
| `tools/genai/thresholds.json` | 覆盖率下限；`null` 表示放弃某个维度，这是唯一的出口，而且它在文件里看得见。同时还有 `e2e` 上限 —— 而**上限缺省不等于放弃**，缺了就按随插件发出的 `5` / `0.2` 算 | `thresholds_missing` |
| `tools/genai/e2e.json` | `url` 与 `contains`：应用的一个端点，加上只有它自己的响应才带的标记。端点不答 200 时再加 `status`。**它在首次验收跑之前到位就行，不是装机时的义务** —— 全新项目没有端口，也没有任何值得拿来匹配的响应内容 | `genai.e2e` 的开工条件返回 `config_missing`，而开工条件失败消耗为零 —— 这一步只是开不了工 |
| 一个 `openspec/` 目录 | `openspec/changes/` 与 `openspec/specs/` | 四个原子都会返回 `unreadable` |
| 兄弟目录 `<project>_genai/` | 一个需求一个目录，状态写在各自的 frontmatter 里 | backlog 那几个原子返回 `unreadable` |

这个划分就是要点所在。**项目报事实；随插件发出的定义作判决。** 自己判自己的项目等于没有门，而能改动算术的一轮
不算被它衡量过 —— 所以判定逻辑住在 `.flow/genai/`，那里不进 git、由插件重新安装。只有下限归项目，而且在一个
本轮也不许编辑的文件里。

## 3. 检查接口

任何一步做的任何检查，都是一个原子，在同一个入口后面：

```bash
node .flow/genai/check.mjs <atom> [--flag value]
```

**这个路径相对项目根，而这是引擎的性质，不是一条约定。** 门命令跑在 `checker.cwd ?? projectRoot`，所以无论调用
方站在哪里，同一个固定路径解析结果都一样。

线上格式是 stdout 上的一个 JSON 文档：`result` 给出标签，其余每个键都是它背后的事实。门通过
`label_from: result` 读标签，而**整个对象会落进事件日志** —— 这正是让一次拒绝在工作区早已变样之后仍可复现的东西。

标签受两条规则约束，两条都在插件的 `AGENTS.md` 里以规则形式写着：checker 永远 exit 0（非零退出会被引擎报成
`failed`，标签就丢了），以及一条规则的 `on_result` 必须恰好覆盖 `values + [failed, unexecutable]`。

### 十五个原子

| 原子 | 标签 | 谁在读 |
|---|---|---|
| `backlog-status --status <s>` | `present` · `absent` · `unreadable` | `genai.spec` 进入 · `genai.accept` 门 · `genai.release` 进入 |
| `open-changes` | `present` · `absent` · `unreadable` | `genai.archive` 进入 · `genai.archive` 门 · `genai.accept` 进入 |
| `spec-deltas` | `present` · `absent` · `unreadable` | `genai.implement` 进入 |
| `openspec-valid --scope <changes\|specs>` | `satisfied` · `validation_failed` · `totals_unreadable` · `openspec_unavailable` | `genai.spec` 门 · `genai.archive` 门 |
| `backlog-claimed` | `agreed` · `unclaimed` · `none_active` · `unreadable` | `genai.spec` 门 |
| `worktree` | `clean` · `dirty` · `unreadable` | `genai.code-review` 进入 · `genai.merge` 进入 · `genai.archive` 进入 |
| `metrics` | `satisfied` · `tests_failing` · `no_tests` · `too_many_skipped` · `coverage_below_floor` · `metrics_missing` · `metrics_unreadable` · `thresholds_missing` | `genai.implement` 门 · `genai.merge` 门 |
| `spec-scenarios` | `unique` · `unnumbered` · `duplicated` · `count_mismatch` · `unreadable` | `genai.spec` 门 |
| `arch-doc` | `complete` · `no_decisions` · `decision_incomplete` · `external_reference` · `background_over_ceiling` · `unreadable` | `genai.write-arch-docs` 门 |
| `e2e-manifest` | `accounted` · `unaccounted` · `over_ceiling` · `manifest_missing` · `manifest_malformed` · `unreadable` | `genai.e2e-author` 门 |
| `e2e-mapping` | `matched` · `title_missing` · `file_missing` · `unreadable` | `genai.e2e-author` 门 |
| `e2e-report` | `green` · `product_failure` · `test_failure` · `infra_failure` · `coverage_short` · `db_evidence_missing` · `report_missing` · `report_malformed` · `unreadable` | `genai.e2e` 门 |
| `app-identity` | `identified` · `wrong_service` · `unreachable` · `config_missing` · `config_malformed` | `genai.e2e` 进入 |
| `signature-archive` | 不是检查 —— 打印一个 sha256 | `genai.accept` 的产出签名 |
| `signature-e2e-suite` | 不是检查 —— 对 manifest 点名的那些测试文件打印一个 sha256 | `genai.e2e-author` 的产出签名 |

**原子只报事实，绝不报判决**，这正是同一个实现能服务两个想要相反答案的调用方的原因：`open-changes` 返回
`absent`，对归档是 `pass`，对验收是 `ready`，而任何地方都没有取反开关。极性住在调用方的 `on_result` 里。

`e2e-report` 是唯一一个标签在两个**去处**之间做选择、而不是在两条消息之间做选择的原子：`product_failure` 是一个
路由到 `genai.implement` 的 `reject`，`test_failure` 是一个路由到 `genai.e2e-author` 的 `delegate`。边只按判决
路由 —— 不看报告字段，也不看门的标签 —— 所以这两个桶就是图能采取行动的全部，验收跑自己弄错的其余部分都归它自己修。

有四个原子无论被谁调用都带超时，因为它们要拉起外部进程：`openspec-valid` 与 `spec-scenarios` 给 120 秒
（后者要向 openspec 要一个场景总数），`e2e-report` 给 120 秒，`app-identity` 给 30 秒，`metrics` 给 600 秒 ——
一整套带覆盖率的测试。

`signature-e2e-suite` 存在的原因是 e2e 测试**没有固定位置** —— 它们放在项目原本就存放测试的地方 —— 所以没有
locator 能找到它们，框架也就没有东西可量。manifest 点名了那些文件，签名就取自它们的内容。没有它，
`genai.e2e-author` 的防空转规则只要动一下 manifest 就能满足；而这一点很要紧，因为通往这一步的 `delegate` 回边
不花耐心。

`worktree` 忽略未跟踪文件，这是承重的而非顺带的：评审那一步**故意**把记录留在未提交状态，由合并那一步来提交。
这条性质也正是 `genai.code-review` 能带一条 `clean-tree` 开工条件的前提 —— 该步自己写下的记录推翻不了它。

有三条开工条件收窄了 `when`，没有用 `always` 缺省，因为它们会被自己那一步推翻：`genai.spec` 把它进入时依据的
ready 项认领掉（`first_attempt`，它是根步骤），`genai.archive` 把它进入时依据的 change 折叠掉、并把工作区弄脏
（`upstream_reran`，它有一个会重跑的上游）。其余都是每次派发都问，这正是那几条挡在不可逆动作前面的规则值得依赖的原因。

## 4. 十三个步骤

名册与执行者。**进入条件和门条件不在这里重复** —— 它们在各自的 `node.yaml` 里，紧挨着解释「为什么长这样」的注释；
在这棵树里抄一份，第一次有人改它就腐烂了。

| 步骤 | kind | 执行者 | 产出 |
|---|---|---|---|
| `genai.spec` | produce | 子代理 `genai-spec-writer` | openspec 变更与它们的 spec 增量 |
| `genai.spec-review` | judge | 子代理 `genai-spec-reviewer` | 每个变更一份 `spec-review.md` |
| `genai.write-arch-docs` | produce | 子代理 `genai-spec-writer` | 有东西要裁的变更，每个一份 `genai/DECISION.mdx` |
| `genai.arch-decision` | judge | **人**，channel `stdout` | 记录下来的裁决，由 `fsx human` 自己写入 |
| `genai.implement` | produce | 子代理 `genai-developer` | sprint 分支上的提交 |
| `genai.e2e-author` | produce | 子代理 `genai-e2e-author` | e2e 测试套件，以及每个变更一份 `genai/e2e-manifest.md` |
| `genai.code-review` | judge | 子代理 `genai-code-reviewer` | 每个变更一份 `review.md` |
| `genai.e2e` | verify | 子代理 `genai-e2e-runner` | 每个变更一份 `genai/e2e-report.md` |
| `genai.merge` | effect | main | 合并提交 |
| `genai.archive` | produce | main | 折叠后的主 spec |
| `genai.update-project-docs` | produce | 子代理 `genai-doc-writer` | 项目的文档树（observed 产物，由命令签名） |
| `genai.accept` | judge | 子代理 `genai-requirement-checker` | 已归档的需求（observed 产物，由命令签名） |
| `genai.release` | effect | main | changelog，以及全轮唯一一次版本号变更 |

有三步跑在 `main` 上而不是子代理里，因为这三步都需要把整轮尽收眼底。`.flow/workflows/genai-sprint.yaml` 是白名单：
引用了名单之外任何东西的图，在创建时就会被拒。

## 5. 这套流程依赖两个外部工具的哪些行为

两个都是第三方，而且两处依赖的都是容易搞错的行为：

**fsx.** `brief.md` 只能插两个槽 —— `{{report}}` 与 `{{state}}` —— 而这十份定义一个都没用：上游产物、
产出要求、驳回意见三段由框架的契约块**无条件**印出，没有插槽能指名它们。brief 里留着已退役的插槽是
`fsx check` 的一条 error，不再是一次静默的重复。进入条件失败时**消耗为零** —— 不消耗判决、不消耗耐心、
不消耗尝试次数，这正是它们可以放心添加的原因。门
命令拿不到**任何**变量：没有图变量、没有实例后缀、没有注入的环境。所以每个检查只能从 `$PWD` 或从 git 推出自己的
上下文 —— 这一个事实同时解释了为什么 `.flow/genai/check.mjs` 是固定路径，以及为什么兄弟目录的名字是承重的。

**openspec.** 它的退出码不可信：`validate` 报了失败仍然 exit 0，`archive` 把警告带过去也仍然 exit 0。所以
`lib/openspec.mjs` 读输出、解析 totals 行，绝不看退出码 —— 而缺少 totals 行是它自己的一个标签
（`totals_unreadable`）而不是通过，因为那意味着什么都没被真正校验过。由此得出的规则写在插件的 `AGENTS.md` 里：
驱动 openspec 自己的命令，绝不把它的规则在本地重新实现一遍。

这条规则只有一处被弯了，而且是明知故弯。`openspec show --json` 给出的是一个场景的 `rawText`，**把标题丢掉了**，
所以场景编号没法从 openspec 自己的输出里读 —— `lib/e2e.mjs` 从 markdown 里读，并尽可能贴着 openspec 的读法
（requirement 内部任意一个不在围栏里的四级标题）。让这件事保持诚实的办法是向 openspec 要场景**总数**，两边不一致
就报 `count_mismatch`，而那条消息说的是「定义错了」而不是「spec 错了」。给别人的格式加第二个解析器是负债；一个
拿第一个来校对自己的第二解析器，是有界的负债。

## 6. 版本耦合

`.flow/nodes/` 和 `.flow/genai/` 是**一个整体**。判定器停在比调用它的定义更旧的版本上，会产出 `unexecutable`
或一个没被处理的标签，所以重装定义就意味着在同一步里重拷判定器。
