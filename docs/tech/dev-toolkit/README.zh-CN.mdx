> 十九个原子级开发能力，分五类。每一个都独立成立、触发于自己的主题，并且对"谁调用了它"不作任何假设。
> **权威来源：`src/plugins/dev-toolkit/skills/`。** 版本 3.0.0；没有 agent，没有 hook。

## 核心思路

**这些 skill 都不知道是谁调用了它。** description 回答的是*什么时候该用它*，绝不回答*谁会用它* —— 这正是这套东西
可组合的原因。无论是人在问、流水线在派发、还是别的 skill 在委托，行为完全一致。

对你的实际影响是：**你很少需要点名。** 把场景说出来，对的那个 skill 自己就加载了。点名是留给"你想把某个特定视角
套到一个它本来不会触发的东西上"的情况。

第二个思路会改变你读这里每一份结论的方式：**检查只报告，不做门。** 一个 check skill 给出结论就停。它绝不决定这个
结论要不要拦住什么，因为**阈值属于做拦截的那一方** —— 而一个自己决定自己后果的检查，没法在另一个标准下复用。

## conventions —— 产物应该长什么样

六个 skill，回答"在**这里**这东西该怎么写"，依据是项目**记录下来的**约定，而不是从旁边的代码里推测。

| Skill | 什么时候伸手 | 它带的深度 |
|---|---|---|
| `coding-guideline` | 这东西叫什么、模块该不该拆、函数遇到错误怎么处理、注释写多少 | `references/` 下 11 份语言/框架指南 |
| `dba-guideline` | 这个列类型对不对、这个索引值不值、这次迁移能不能在大表上线上跑 | `mysql.md`、`postgresql.md` |
| `devops-guideline` | build/test/lint/run 走哪一个统一入口、什么是本地容器、什么是要发出去的 | `make.md`、`dockerfile.md`、`docker-compose.md` |
| `docs-guideline` | 活已经交付了，这份持久知识该放哪儿 | `taxonomy.md`、`readme-templates.md` |
| `middleware-guideline` | 这个服务怎么找到自己的配置、配置源不可达时怎么办、凭据从哪来 | `nacos.md`、`monitoring.md` |
| `spec-guideline` | 这次改动在**开工之前**必须钉死哪些东西 | `stable-ids.md` + 一个 `check-spec.mjs` 检查器 |

**用法。** 问问题，不要要文档："这两个该是两个模块还是一个"比"读一下编码规范"路由得更准。这些 skill 提供的是
**关于东西该长什么样的判断** —— 执行一个形状已经定了的改动是另一件事，所以它们会告诉你形状然后停下。

**最佳实践。** 当规范和你周围的代码不一致时，**那本身就是一个发现**，不是一个悄悄决定一下的分歧。说明你按哪个走了。

## methods —— 怎么跑一个有效的循环

四个 skill，带的是循环而不是意见。

| Skill | 循环 | 什么时候伸手 |
|---|---|---|
| `grill` | 一次一个苏格拉底式问题，每个都自带你推荐的答案 | 需求含糊，直接开工等于猜 |
| `tdd` | 红 → 绿 → 重构，而且要确认失败的测试是**因为预期的原因**失败 | 要造新行为 |
| `debug` | 三个不同的循环 —— 日志、退出码收敛、CLI 调试器 —— 跑到证伪为止 | 一个故障的原因还不明显 |
| `e2e-test` | 驱动真实 UI，**同时**验证真正落进数据库的东西 | 一条流程需要端到端被证明 |

`tdd` 带 8 套工具链的接线；`debug` 带 9 套；`e2e-test` 带 6 个平台外加 `db-verification.md`。

**用法。** `grill` **一次只问一个问题**，而且绝不问它自己能查到的东西 —— 它开口问了，说明那个答案确实只能由你给。
`debug` 会先建立可复现信号再进任何循环；跳过这步，调试就变成"读代码读到看见一处不顺眼"。

**最佳实践。** `e2e-test` 存在的全部理由在后半句：**一个绿色的 UI 断言，坐在一行从未被写入的数据之上，是一个什么都
没测到的通过。** 如果你只想验 UI，请说清楚，并且知道自己放弃了什么。

## 流程约定

`vcs-workflow` —— **决定这个项目里怎么分支、怎么定版本、怎么发**：worktree 里的 feature 分支、合进集成分支、向受保护
的 main 提 MR，以及 bump → merge → build → publish 的发布次序。深度在 `release.md` 和 `submodule.md`。

**最佳实践。** 它会先识别仓库形态，这一步不是仪式 —— 一个带 submodule 的仓库和一个单仓库，对"这个分支该开在哪"的
正确答案是不同的。

## checks —— 拿一个产物，给一个结论

五个 skill。每个都按严重度排序返回发现，而且**没有一个会拦住任何东西**。

| Skill | 对什么给结论 | 备注 |
|---|---|---|
| `a11y-check` | 无障碍，每条发现映射到一条 WCAG 成功准则 | **把自动化查不了的准则列成待办**，而不是静默略过 |
| `glossary-conformance` | 这次改动用的词是否与某个限界上下文登记的术语表一致 | 永远只针对**一个**上下文 |
| `perf-budget` | 延迟、查询数与 N+1、包体积，以及项目自己定预算的其他维度 | 每个维度报「实测 / 阈值 / 基线+差值」—— 一个孤零零的数字不是结论 |
| `security-scan` | SAST 模式、依赖 CVE、硬编码密钥 | 一趟跑三类 |
| `smell-scan` | 架构与代码坏味道，输出一份排序后的重构候选 | 带**删除测试**和一份行为保持交叉引用 |

**用法。** 给检查一个目标，有标准的话给标准。没有标准它照样报告；它只是不会假装自己能决定。

**最佳实践。** 读清楚一份干净的报告**证明了什么**。`glossary-conformance` 和 `a11y-check` 都在自己正文里写明了各自的
局限，原因就在这里：自动化跑完"没有发现"不等于"合规"，而把它当成合规，正是这两个 skill 被设计出来要防的失败。

## grounded research —— 去看，而不是回忆

三个 skill，一个原则：关于一个真实系统的答案，应该建立在**观察**上，而不是建立在回忆、或建立在可能已经过时的文档上。

| Skill | 去看什么 | Playbook |
|---|---|---|
| `research-api` | 真实端点 —— 先发现 OpenAPI/Swagger 规格，再探测，**先只读** | `probe-playbook.md` |
| `research-data-source` | 真实数据 —— schema、样本行、取值分布、体量，**只读** | `explore-playbook.md` |
| `research-source-code` | 真实依赖 —— 按精确 tag/commit 克隆，并记录到 SHA 级的出处 | `study-checklist.md` + `clone-ref.sh` |

**最佳实践。** 当"搞错了代价很大"而且问题是事实性的时候用它们（"这一列实际存的是哪些值"、"这个库超时的时候到底怎么
做"）。每一个都有明确的安全红线 —— 先只读、不做破坏性探测 —— 而这些红线不会因为好好说话就松动。

## 相邻的怎么选

容易混的几对，以及分开它们的那个判据：

| 你正要… | 但真正的问题是… | 该用 |
|---|---|---|
| 让 `coding-guideline` 把改动做掉 | 谁定形状，谁执行 | 规范定形状，然后去实现 |
| 把 `smell-scan` 当合并门 | 阈值归谁 | `smell-scan` 只报告；门是你的 |
| 拿一句含糊的抱怨去问 `debug` | 症状到底钉住了没有 | 先 `grill`，再 `debug` |
| 问 `spec-guideline` 代码对不对 | 这是设计的事还是实现的事 | `spec-guideline` 判的是设计的达标线 |
| 回忆某个库的行为 | 搞错的代价是否高于去看一眼 | `research-source-code` |

一条典型链路，每个箭头都是交接而不是调用：`grill` → `spec-guideline` → `tdd` → 出问题时 `debug` → 某个 check
skill → `vcs-workflow` 发出去。

## 深度内容在哪

每个 skill 都把自己的 `SKILL.md` 控制在上下文预算内（500 行，由 `make verify-skills` 强制），并把深度推进
`references/`。`SKILL.md` 在 skill 每次触发时都**整份**加载；`references/` 只在正文把模型指过去时才加载。正是这个
拆分，让一个 skill 能覆盖十一种语言，而不必在每次使用时都为十一种语言付费。

有两个 skill 随附可执行文件：`spec-guideline/scripts/check-spec.mjs` 和
`research-source-code/scripts/clone-ref.sh`。

有七个 skill 在 `evals/` 里带触发 fixture —— 它们从不随产物发出，只在本仓库内用于测量一条 description 是否路由得对。
