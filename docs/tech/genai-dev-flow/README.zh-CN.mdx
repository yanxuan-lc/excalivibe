> 一整套开发流程：需求进来，一个版本出去，每一步都被某个可重跑的东西门控住。
> **权威来源：`src/plugins/genai-dev-flow/`** —— 4 个 skill、4 个 agent、7 份步骤定义。
> 版本 3.0.0。引擎侧的契约在 [`../flow-contract/`](../flow-contract/README.zh-CN.mdx)；本文是那 4 个 skill 的手册，
> 以及一轮到底怎么跑起来。

## 你得到什么

不是一堆工具，而是**一条流程**，建立在两个容易搞错的分离之上。

**"想要什么"和"怎么建出来"是两件事。** 需求住在 `<project>_genai/`，仓库的同级兄弟目录。spec、变更、文档和代码住在
仓库里并且一起版本化，所以任何一个 commit 上这四者都是一致的。一条需求横跨很多版本，且不对应任何 commit —— 把它放进
仓库，立刻有两个后果：每个 worktree 都带着一份自己看不见的副本，而合并一批需求必然在那份共享清单上冲突。

**一个 sprint 是发布单位，不是并发单位。** 一轮就是一个版本号，只 bump 一次，而它可以承载横跨多个变更的多条需求。
这正是"按变更走"的流程一直丢掉的区分：在单个变更的上下文里，那个变更**就是**一切，所以做完它看起来就像做完了一轮。
修好这件事的办法不是反复强调"不要 bump 版本" —— 在本仓库里，一条明确排除了某场景的 description 仍然 5 次中 5 次在
该场景上触发 —— 而是**在上游根本不提这个话题**，并把唯一**被允许** bump 的那一步放在最后。

## 四个 skill，你要的是哪个

前三个之间的划分是**学 / 装 / 跑**，这是刻意的：一份顺手也能开跑的手册，会在没人想读的时候被读；一个顺手也教学的
驱动器，会让每一轮都为那段解释付费。

| Skill | 命令 | 什么时候用 |
|---|---|---|
| `genai-guideline` | — | 想搞清楚某一步被什么门控住、某道门够不够强、或者项目自己要提供的那几样东西怎么写 |
| `genai-init` | `/genai-dev-flow:genai-init` | 一个项目要接线，一次。**只在被点名时才触发** |
| `genai-flow` | `/genai-dev-flow:genai-flow` | 一轮该开始了、已经在跑、或者某一步过不去 |
| `genai-backlog` | — | 有人描述了他想要建的东西，或者问题是"接下来该拾起哪个" |

### genai-backlog

**判断一个说出口的意图该放在哪里、以及它处于什么状态** —— 记下来、澄清到可以开工、给候选排序、上线后归档。
`<project>_genai/backlogs/` 下一个需求一个目录，里面是 `brief.md`（目标、为什么、已定、不做、待解问题）和 `log.md`，
状态写在这个需求自己的 frontmatter 里。

**最佳实践。** 让一个需求在 draft 里待着，直到它的待解问题有了答案。`ready` 是 `genai.spec` 的进入条件在找的东西，
所以把一个含糊的东西提上去并不会让一轮开始得更快 —— 它会让一轮在后面某道门上被打回，而耐心已经花掉了。

### genai-init

**把流程装进一个项目，一次。** 它的召回刻意收得很窄 —— 只有点名才触发 —— 因为它会往仓库里写东西，而这种事不该由
一句顺带提及来触发。

它把什么装到哪里、每一块归谁，在 [`../flow-contract/`](../flow-contract/README.zh-CN.mdx)。归**项目**的那两块是一个
`genai-metrics` make 目标和 `tools/genai/thresholds.json`。

**最佳实践。** 让它来创建那两样；**不要手写步骤定义**。而且要老实回答它唯一一个真问题 —— 覆盖率下限。
`90 / 90 / 100` 对一个从零开始的项目是对的；对一个已经有代码的项目，要**按它今天实际测出来的数**和人商定，因为
**本轮不许编辑那个文件**，所以一个高于项目现状的下限会拒掉每一轮，而且没有任何东西能补救。

### genai-flow

**驱动一轮**：建图、派发每一步、给结果判决、路由返工。它**先检测再询问** —— 项目已经装好了的话，它直接开跑。

图是一条直线加一条回边：

```
spec ─▶ implement ─▶ code-review ─▶ merge ─▶ archive ─▶ accept ─▶ release
              ▲            │
              └── reject ──┘
```

耐心是 5，**整批共享**，所以返工三个变更各一次就花掉三点。

**最佳实践 —— 四条路由规则，破一条就是一轮的代价：**

- **绝不在 `delegate` 上路由。** 一个没有匹配边的 `delegate` 判决会把图硬锁死。
- **绝不把 `pass` 边往回画。** pass 边是依赖；往回指一条就把图变成了环。
- **`reject` 的自返工不需要边。** 多余的自环无害；缺一条**跨节点**的 reject 边则不然 ——
  `genai.code-review → genai.implement` 就是那条要紧的。
- **绝不把 `genai.accept` 用 `reject` 往回路由。** 它判的是整批，所以一条回边会把整批重新打开。让它挂起、交给人处理
  才是设计意图。

**中途发现新活：绝不加进本轮。** 图是固定的，而 `genai.spec` 已经过了。放进 backlog。

### genai-guideline

**手册本身。** 它回答七步各自被什么门控住以及为什么、项目要提供什么、度量协议的全文，以及那些坑。给项目接线之前读它，
某个判决需要解释时读它。

## 四个 agent

每个要产出或要判断的步骤都会派发给一个子代理，而**它们之间的划分不是组织架构上的 —— 每一个都必须运行在一个"没有生产
过它正在评判的东西"的上下文里。** 一个 spec 作者去验收自己写的需求，是在检查他早已说服过自己的活。这份独立性是这个
分离买到的唯一东西，也是它们不能合并成更少个的原因。

| Agent | Tier | 判断或产出 |
|---|---|---|
| `genai-spec-writer` | top | 决定哪些需求归进一份 spec、哪些各自独立，然后写增量 |
| `genai-developer` | standard | 照 spec 实现并提交；由项目的门来决定什么时候算完 |
| `genai-code-reviewer` | standard | 正确性、可维护性，以及**改动有没有越出这个变更本来的范围** |
| `genai-requirement-checker` | top | 读**当初要的**而不是后来规定的，判断有没有东西被落下 |

在 Codex 端，插件不能捆绑 agent，所以要手工装到 `~/.codex/agents/` —— 见 `make install-codex`。

## 会赔掉一整轮的坑

这些都不是假想，每一条都真发生过。

- **`openspec validate` 在有条目失败时仍然 exit 0。** 两道 openspec 门读的都是 totals 行而不是退出码。任何建立在
  CLI 之上的新检查都需要同一种怀疑：先确认那条命令真的会失败，再去相信建在它上面的门。
- **`--strict` 数的是字符，不是含义。** 一段用 38 个汉字把事情说全的 Purpose，过不了 50 字符的下限。用中文写 spec 的
  项目会反复撞到。
- **评审者不得提交自己的记录。** 一个判决是针对交付给它的那个确切 commit 记录的，所以在那一步里发生的任何提交都会让
  正在给出的判决失效 —— 而一个已通过的步骤不能重跑。记录保持未提交状态，由合并那一步收走。**没有任何顺序能绕开
  这件事**；前提在派发那一刻就固定了。
- **`.flow/` 整个被 ignore，包括定义。** 它们在这个插件里已经被版本化了，所以跟踪它们等于在每个仓库里放一份已被版本化
  产物的第二副本，还会让切分支改变引擎的契约、让改定义弄脏工作区、让合并在白名单上冲突。
- **在图运行期间改定义会让这次运行失效。** 哪怕只改一个步骤 brief 里的注释也算。先把这一轮跑完或中止。

## 这套流程不做什么

它不替你选测试框架、不替你决定版本号（`genai.release` 读 commit 自己决定并记录理由）、也不在没被装进去的项目里工作。
另外它**在这里跑不起来**：本仓库没有测试、没有 runner、没有 `genai-metrics` 目标，所以 `genai.implement` 会返回
`metrics_missing`。
