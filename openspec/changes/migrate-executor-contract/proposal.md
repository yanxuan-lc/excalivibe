## Why

flow-scratch changed the `executor` contract in a node definition (upstream `d64d37b`): a bare
string is no longer accepted, and every declaration must name a protocol. All fourteen definitions
`dev-workflow` ships still use the old form, so they now fail to load:

```
executor  executor must declare a protocol; the bare string `main` is not one  [executor_legacy_string]
→ Write it as `{protocol: subagent, params: {name: main}}`.
  The protocols are main / subagent / human / command / acp / a2a
```

`make check` stays green because it only verifies our own compile is in sync — the engine's contract
is not something it can see. So the artifacts look healthy and are not. Anyone installing the flow
today gets fourteen definitions that `fsx check` rejects.

Everything else planned for `dev-workflow` sits behind this. A new node written against the old
form is a second thing to migrate, so this goes first and alone.

## What Changes

- **BREAKING** Fourteen `node.yaml` files move `executor` from a bare string to the protocol form.
  Breaking for anyone who installed the flow before this — their `.flow/nodes/` still holds the old
  definitions, and refreshing them is the fix.
- The installer's executor summary stops parsing the field with a line-oriented regex, which the
  structured form breaks.
- `install-dev-workflow/SKILL.md`'s executor table is restated in the new vocabulary.

Deliberately **not** in this change: no node is added, removed, split, or re-scoped; no gate rule,
locator, input, or output moves. The three-segment split, the delivery segment, `genai-init` and the
intent-routing skill all follow in their own changes.

## Capabilities

### New Capabilities

None — this is a tooling migration.

### Modified Capabilities

None. No externally observable behaviour of the plugin changes: the same fourteen steps, the same
executors, the same gates. Only the notation the engine reads. `skip_specs: true` is set in
`.openspec.yaml` accordingly.
